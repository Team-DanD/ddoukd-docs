- 함께 보는 파일: [scenarios.md](scenarios.md)(검증 시나리오), [results-template.md](results-template.md)(결과 기록 양식)

이 문서는 **구조를 정하지 않는다.** 무엇을 확인하면 정할 수 있는지를 적는다. 구조의 채택과 production 구현 착수는 결과를 본 뒤 서현과 민수가 정한다.

## 무엇을 검증하나

질문은 하나다. **Expo 한 코드베이스에 웹 전용 파일을 섞는 안(A-2)으로 운영자 화면의 핵심 흐름을 웹과 앱에 낼 수 있는가.**
막히면 그 부분만 분기해서 풀 수 있는지, 아니면 구조를 바꿔야 하는지를 가른다.

| 후보 | 이 검증에서의 역할 |
| --- | --- |
| A-2: Expo Router + react-native-reusables + 필요한 `.web.tsx` | 먼저 만들어 보는 대상 |
| 지금의 Vite 웹(`ddoukd-web`)으로 운영자 화면까지 | 비교 기준. 시나리오 5에서 같은 흐름을 비교한다 |
| 웹·앱 분리(B) | A-2가 막혔을 때의 선택지. 이번에 만들지 않는다 |

조사 문서의 머지는 채택이 아니다. 이 검증의 결과가 채택의 근거가 된다.

## 범위

들어가는 것

- 사업장 운영자 화면의 한 흐름: 로그인 → 회원 검색·선택 → 예약 입력 → 결과(성공 또는 오류) → 예약 상세
- shop-key 경로로의 직접 진입과 새로고침, 샵이 다를 때의 격리
- 공개 캘린더는 **경로와 노출 항목만**. 톤과 구성은 정해지지 않았으므로 검증하지 않는다
- 포커스, 한글 입력, 키보드, 44px 영역, 1px 선 같은 디자인 시스템의 기본 조건

들어가지 않는 것

- 회원권(슬라이스 1에 없다), 그룹 수업, 대기
- 백오피스(이 디자인 시스템 밖이고 기성 UI 라이브러리로 만든다)
- 실제 서버 연동. 가짜 데이터로 화면 동작만 본다(아래 "가짜 데이터로 확인할 수 없는 것")
- 화면의 완성도. 톤을 맞추는 것은 시나리오 4의 상태 갤러리 하나로 본다

## 착수 전에 정할 것

아래는 이 문서가 정하지 않는다. 검증을 시작하기 전에 민수(와 필요한 것은 서현)가 정해 [results-template.md](results-template.md)의 맨 위에 적는다.

| 정할 것 | 누가 | 메모 |
| --- | --- | --- |
| 지원할 OS와 브라우저의 범위 | 민수 | 예: iOS Safari, Android Chrome의 어느 버전부터. 검증 기기도 함께 |
| 검증에 쓸 시간의 상한 | 민수 | 상한을 넘으면 범위를 줄이거나 멈추고 결과를 적는다 |
| 성능의 허용 기준 | 민수 | 초기 JS 용량, 첫 화면까지의 시간. 숫자를 먼저 정해야 통과·실패를 가를 수 있다 |
| 검증에 쓸 패키지 버전 묶음 | 민수 | 아래 "버전" 참고. 조사 문서의 버전을 그대로 복사하지 않는다 |
| 운영자 화면을 웹으로 꼭 내야 하는지, 앱 출시 시점 | 서현 · 민수 | 기존 결정은 "웹 먼저, 앱은 검증 후"다. 바꿀 근거가 없으면 유지한다 |

## 버전

각 패키지의 최신 버전을 따로 고르지 않는다. **Expo가 권장하는 한 묶음**을 쓰고 lockfile을 남긴다.

- 조사 시점(2026-10-05)에 확인한 값: Expo SDK 57은 React Native 0.86.3, React 19.2.3이다
- 시작할 때 Expo의 버전 대응표를 다시 확인한다. 그사이 SDK가 올라갔을 수 있다
- NativeWind 4, NativeWind 5(RC), Uniwind는 서로 다른 조합이다. 하나를 골라 시작하고 바꾸면 결과에 적는다
- 웹 쪽 검증은 `ddoukd-web`에 맞춰 pnpm으로 한다. `ddoukd-app`의 패키지 매니저는 정해지지 않았다

후보를 쓰려고 Expo가 지원하지 않는 React Native 버전을 강제해야 하면 그 조합은 멈춘다.

## 진행 순서

| 순서 | 할 일 | 통과·중단 기준 |
| --- | --- | --- |
| 0 | "착수 전에 정할 것"을 채운다 | 비어 있으면 통과·실패를 가를 수 없다 |
| 1 | 버전을 고정하고 웹 production export와 iOS·Android 빌드를 낸다 | Expo 권장 조합에서 다시 만들 수 있어야 한다 |
| 2 | [시나리오 A~E](scenarios.md)를 A-2로 만든다 | 한글 입력, 키보드, 스크롤, 뒤로 가기, 입력 보존, 스크린리더까지 본다. 화면 전체를 갈라야 하거나 라이브러리 내부를 고쳐야 하면 비용을 적는다 |
| 3 | 실제 호스팅에 올려 [시나리오 F](scenarios.md)(경로와 테넌트 경계)를 본다 | 새 shop-key에 다시 배포하지 않고 들어갈 수 있어야 한다. 다른 샵의 세션이나 캐시가 섞이면 실패 |
| 4 | 상태 갤러리 하나로 디자인 조건을 본다([시나리오 G](scenarios.md)) | 360px, 긴 한국어, 글자 확대, 오류와 포커스 동시, 시트 안 입력 |
| 5 | 같은 흐름을 지금의 Vite 웹으로도 만들어 비교한다 | 같은 데이터·폰트·기기·네트워크에서 초기 JS와 폰트 용량, 첫 화면, 조작 응답 |
| 6 | 두 쪽에 같은 변경을 넣어 본다(예: 회원 검색 조건 하나와 필드 오류 하나 추가) | 고친 파일 수, 플랫폼 분기, 확인에 든 시간 |

2번에서 버튼과 입력 필드만 확인하고 "react-native-reusables가 된다"고 적지 않는다. Dialog, Select, 시트의 조합과 production 빌드가 들어가야 한다.

## 막혔을 때

1. 그 컴포넌트만 웹 전용 파일(`.web.tsx`)로 분기해서 풀 수 있는지 먼저 본다
2. 풀리면 든 비용(파일 수, 시간)을 적고 계속한다. 접근성이나 CSS 문제 하나를 구조 전체의 실패로 넓히지 않는다
3. 화면 전체를 플랫폼별로 따로 만들어야 하면 거기서 멈추고 결과를 적는다. 그것이 "A-2가 이 흐름에서는 안 된다"는 근거다
4. 시간 상한을 넘으면 범위를 줄이고, 줄인 범위를 결과에 적는다

## 가짜 데이터로 확인할 수 없는 것

가짜 API로 화면이 돈다고 해서 아래가 검증된 것은 아니다. 결과 양식에서 따로 적는다.

- 서버의 테넌트 격리(토큰의 shop과 URL의 shop-key 대조, 다른 샵 요청에 403)
- 동시 예약에서의 정원 보호, 세션과 예약의 한 트랜잭션
- 공개 캘린더 응답에서 비공개 값이 빠지는지

화면 쪽에서 볼 수 있는 것은 "샵마다 토큰을 따로 보관하는가", "다른 샵 경로로 갔을 때 앞 샵의 화면이나 캐시가 보이지 않는가"까지다.

## 이 문서가 정하지 않는 것

- A-2의 채택, Vite로의 전환, 웹·앱 분리, 모노레포와 공유 패키지의 구조
- 앱 출시 시점, 지원 OS·브라우저, 성능 허용 기준, 시간 상한
- 예약 취소·노쇼를 허용하는 시점, 강사 가용시간 밖 시각의 처리, 검색·페이지 방식, 오류 코드
- 공개 캘린더의 톤, 샵 로고·색 커스텀, 회원권 정책

시나리오에서 이런 값이 필요하면 **가짜 데이터용 가정**이라고 표시하고 쓴다. 가정은 결정이 아니다.

## 준비가 끝났다고 보는 기준

민수가 이 폴더만 보고 첫 시나리오를 실행할 수 있고, 그 결과가 구조 선택의 어떤 근거가 되는지 알 수 있으면 된다.
